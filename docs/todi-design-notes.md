# todi 설계 메모 (PPT 제작용 원천 문서)

## 1. 앱명
**todi (토디)**

- 의미: **TOday's DIscovery**
- 핵심 메시지: 오늘 새롭게 발견할 전시·공연·팝업을 취향과 지역에 맞춰 제안하는 서비스
- 기존 프로젝트명 '오늘의 발견'의 의미를 유지하면서 모바일 앱 아이콘과 서비스 브랜드에 적합하도록 짧게 축약
- 브랜딩 표기: **todi**
- 설명형 서브카피 후보: *Today's Discovery*

## 2. 서비스 범위
- 지역: 서울특별시
- 세부 지역: 서울 25개 자치구
- 사용자는 선호 지역구를 복수 선택할 수 있으며, 선택하지 않으면 서울 전체를 대상으로 추천
- 검색 화면에서는 서울 전체 또는 특정 자치구를 직접 필터링
- 행사 범위: 팝업, 전시, 공연, 페스티벌, 뮤지컬, 연극, 클래식
- 제외: 교육, 강좌, 박람회, 플리마켓, 일반 할인 프로모션, 단순 신규 매장 오픈

## 3. 목표 데이터 구조
메인 운영 구조는 Supabase 중심으로 단순화한다.

```text
공식 출처 / SNS 후보 발견
        ↓
Collector
        ↓
AI 구조화
        ↓
자동 품질 검증
        ↓
중복 제거
        ↓
Supabase
        ↓
todi App
```

Live Feed는 Supabase 데이터가 부족하거나 수집 파이프라인에 장애가 있을 때 사용하는 백업 채널로 유지한다.

## 4. 자동 품질 검증
수동 승인 없이 자동 품질관리한다.

### 처리 단계
1. 공식 출처에서 후보 데이터 수집
2. AI가 공통 Event 스키마로 구조화
3. Rule-based Quality Score 계산
4. 80점 이상 자동 승인
5. 60~79점은 공식 원문과 AI 일괄 재검증
6. 재검증 후 80점 이상만 승인
7. 60점 미만은 사용자 화면에서 제외
8. 행사명 + 시작일 + 장소 기반 중복 검사는 별도의 Hard Gate로 적용

### Quality Score 구성
- 행사명 정상: 10
- 날짜 유효성 및 현재/예정 행사 여부: 20
- 신뢰 가능한 공식 출처: 20
- 장소 정보: 10
- 서울 지역 및 자치구 정보: 10
- 행사 유형 표준화: 10
- 요약 정보: 5
- 관심 태그: 5
- 공식 URL: 10

총점 100점.

### 설계 의도
AI의 판단만으로 승인하지 않고, 결정 가능한 항목은 규칙으로 검증한다.
중간 품질 데이터만 AI가 원문을 다시 대조하도록 하여 자동화와 정확성을 함께 확보한다.

## 5. 추천 알고리즘
초기에는 머신러닝 대신 **Hybrid Weighted Ranking + Diversity Re-ranking**을 사용한다.

### 기본 점수 구성
- 명시적 관심사 일치: 최대 40점
- 선호 서울 자치구 일치: 20점
- 현재 진행 / 시작 임박 여부: 최대 15점
- 신규성: 최대 10점
- 사용자 행동 기반 암묵적 취향: 최대 15점

### 행동 데이터
- 행사 상세 조회: 선호 신호 +1
- 관심 저장: 강한 선호 신호 +2
- 신호를 행사 유형, 자치구, 관심 태그별로 축적

### 다양성 재정렬
최종 추천 상위 결과에 동일 행사 유형이나 동일 지역이 과도하게 반복되면 패널티를 적용한다.

목적:
- 사용자의 취향을 반영하면서도 새로운 종류의 행사를 발견하게 함
- '발견' 서비스의 정체성 유지
- 추천 결과의 카테고리 편중 완화

## 6. 계정 및 동기화 구조
Supabase Auth를 사용한다.

### v1.0 로그인 방식
- 이메일 + 비밀번호 기반의 단순 회원가입/로그인
- 회원가입 시 아이디/닉네임과 대표 얼굴 아이콘을 선택
- 이메일 인증 절차는 개인용 v1.0에서는 비활성화하여 가입 직후 바로 로그인
- 대표 아이콘 후보: 🙂 😎 😌 🤓 🥳 🫠 🤠 😴
- 닉네임과 대표 아이콘은 Supabase Auth user metadata에 계정별 저장

카카오톡/네이버 소셜 로그인은 외부 개발자 앱 등록, OAuth 키 발급 및 Redirect URL 관리가 추가로 필요하므로 v1.0 필수 범위에서는 제외하고 향후 개선안으로 둔다.

```text
Supabase Auth
     ↓
user_id
     ↓
User Preferences
Favorites
Behavior
```

계정별로 다음 정보를 동기화한다.
- 관심사
- 선호 자치구
- 관심 행사
- 사용자 행동 데이터

RLS를 통해 각 사용자는 자신의 개인화 데이터만 읽고 쓸 수 있도록 한다.

## 7. PPT 설계서의 '향후 개선안'으로 이동할 기능

### 소셜 간편 로그인
- 카카오 로그인
- 네이버 로그인
- OAuth Provider 연동
- 기존 이메일 계정과 소셜 계정 연결

개인용 v1.0은 가입 절차와 구현 복잡도를 줄이기 위해 이메일/비밀번호 방식을 우선 적용한다.

### 행사별 정밀 상세 URL 수집
현재 공식 출처 URL을 제공하되, 개별 행사 상세 페이지의 canonical URL까지 안정적으로 추적하는 기능은 **개인용 v1.0 필수 범위에서 제외**한다.

설계서에서는 다음과 같은 향후 개선안으로 설명한다.
- 목록 페이지 → 개별 행사 상세 페이지 자동 탐색
- 상세 URL 검증
- 예약 URL 분리
- 공식 상세페이지 단위 데이터 갱신
- 변경된 일정/가격/운영시간 업데이트

## 8. SNS 활용 방향
SNS를 DB의 최종 진실값(Source of Truth)으로 사용하지 않는다.

```text
SNS
↓
신규 행사 후보 발견
↓
행사명 / 브랜드 / 키워드 확보
↓
공식 사이트 재검증
↓
품질검증
↓
Supabase
```

SNS는 팝업·브랜드 이벤트를 빠르게 발견하기 위한 Discovery Layer로 정의한다.
